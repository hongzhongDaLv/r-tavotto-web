# 网页发布与回滚

本文件记录独立浏览器版本的发布路径。R-Tavotto 的原本机工作目录保留，网页发布不覆盖其服务、桌面包或科研输入文件。

## 发布范围

GitHub 的 `main` 分支只提交程序源码、许可证、文档和人工示例；`gh-pages` 分支只接收已检查的 `web/dist-browser/` 静态产物。用户脚本、数据、缓存图、分析输出、凭据及回滚快照不进入这两个公开范围。

发布采用 Node `24.19.0`、pnpm `11.19.0` 与 `web/pnpm-lock.yaml`。版本改变时同步 `.nvmrc`、根与 web 的 `packageManager` 和可选 workflow 模板；依赖锁的更改应和对应验证一同提交。

## 首次发布

1. 检查 `git status` 与待发布文件，执行 `pnpm check:public`。
2. 执行 `pnpm install:web`、`pnpm test:public`、`pnpm test:browser`、`pnpm build`。公开包反例检查必须确认私有数据、路径泄露和 localhost 依赖确实被拒绝；保留失败原因，不能通过删除检查来变成绿色。
3. 在本地浏览器测试核心流程，并在实际仓库子路径构建下检查资源、Worker 和导出下载。
4. 创建或连接明确的 R-Tavotto Web 仓库；避免把旧 Tavotto 全目录或真实项目目录作为新公开仓库上传。
5. 把源码提交到独立仓库的 `main`。记录源 SHA，设置 `BROWSER_BASE_PATH=/r-tavotto-web/`、`GITHUB_REPOSITORY=hongzhongDaLv/r-tavotto-web`、`GITHUB_SHA=<该源码提交>` 后重新执行受检查构建；`build-info.json` 必须指向这份对应源码。
6. 将 `web/dist-browser/` 的内容作为普通新提交发布到独立的 `gh-pages` 分支，不把整个源码目录或用户文件复制进去。仓库 Settings → Pages → Build and deployment → Source 选择 **Deploy from a branch**，分支 `gh-pages`，目录 `/ (root)`。
7. 等待 Pages 完成分支部署，记录 gh-pages 发布 SHA 和 GitHub 提供的构建/部署状态；打开公网测试下列流程。构建或 API HTTP 200 不能代替功能验收。源码 SHA、产物提交与公网 `build-info.json` 应对应同一版本。

本次没有运行仓库自定义 Actions 工作流。`docs/templates/pages.yml` 仅为后续可选模板：获得 workflow 授权后才可安装到 `.github/workflows/pages.yml`，并将 Pages Source 改成 GitHub Actions。模板的存在不是 CI 已运行的证据。

GitHub 当前未认证时先在电脑终端执行 `gh auth login --hostname github.com --git-protocol https --web`，完成浏览器设备授权后用 `gh api user --jq .login` 验证。不要把 token、设备凭据或完整认证输出复制到聊天、README、日志或仓库。

## 核心浏览器验收

| 项目 | 实际操作及判据 |
| --- | --- |
| 无本机服务依赖 | 停止或不启动 Node/R localhost 服务，公网网站仍能初始化 WebR 并编辑人工示例 |
| 文件导入 | 从浏览器文件选择器选自包含 `.R`；导入内容能产生明确的 ggplot 对象；取消不进入永久加载状态 |
| 依赖提示 | 缺文件/包/对象时显示明确可处理原因；不能用服务器本机路径代替用户上传 |
| 对象选择 | 文字、柱、分组点及误差棒按其可视几何选择；左侧图层集合不遮挡图内点选 |
| 框选和窗交 | 空白处左→右只选完全包含对象；右→左选择所有相交对象；检查撤销和选择状态 |
| 画布与图框 | 初始页面来自 R 导出大小；调画布改变白色页面边界，图框及文字物理大小不随之缩放；图框可独立调整 |
| 修改重放 | 交互后展示对应 R 修改；撤销恢复；新会话运行导出代码与图形可对照 |
| 下载 | PNG、SVG、PDF及修改代码文件均非空、可打开；下载失败不能显示成功 |
| 刷新与恢复 | 明確区分临时会话、已下载项目和已验证持久化能力；不丢用户未保存文件而假称已保存 |
| 公共边界 | 网络面板没有本机目录查询、私有数据库或产品遥测请求；发布包没有私有数据/路径 |

测试人工示例通过后，再在本机浏览器导入获准的真实项目验证兼容性。真实项目结果只能写入私有验证位置，不能随发布报告中的截图/附件意外公开。

## 保留回滚点

发布前记录当前 main 源 SHA、gh-pages 产物提交、可用网站 URL 和 Pages 部署记录。验证通过的源码提交可建立标记，例如 `web-20261003-01`；标签命名只是例子，应对应实际提交。保留经验证的静态产物历史，原本机项目的快照和私有测试结果继续留在仓库外。

## 回滚操作

先选择已验证的 gh-pages 产物提交，将其静态文件恢复为 **gh-pages 上的一个新提交**，保留历史并推送，触发分支部署。恢复的 `build-info.json` 继续指向它实际对应的源 SHA。不要使用 `git reset --hard`、强制推送或清空私有运行目录来回滚网站。

源码也需要修正时，可在 main 执行普通 `git revert <bad-sha>` 或建立修复提交；重新完成构建与浏览器验收后，以该源 SHA 生成并提交新 gh-pages 产物。main 的修改不会自动构建网站，不能只推源码就声称回滚完成；也不能拿任意旧产物冒充对应的新源码版本。

回滚完成后检查公网 `build-info.json` 的 `revision`，重新做初始化、导入、画布/图框、撤销及导出冒烟。浏览器缓存可能仍显示旧页，应刷新核对版本。网站回滚不会删除浏览器下载的科研文件，也不保证旧项目格式自动兼容新/旧引擎。

## 状态口径

- **构建完成**：锁定依赖与源码可生成通过静态包检查的产物。
- **公网发布完成**：Pages 部署成功，公网能读取该版本。
- **核心功能验收完成**：浏览器的上述操作实际通过，有对应版本与证据。
- **真实项目兼容通过**：特定脚本、数据与包组合已验证；不扩大为任意 R 脚本均兼容。

这四种状态分别记录，不能用其中一种代替其他三种。
